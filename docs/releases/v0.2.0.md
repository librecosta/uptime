# LibreCosta Uptime v0.2.0

Optional persistent DOWN/RECOVERED notifications for HTTP/HTTPS endpoints,
alongside the existing monitoring dashboard and history.

## Optional endpoint alerts

- Send DOWN notifications after consecutive HTTP/HTTPS probe failures (default
  three, configurable from one to ten), then RECOVERED on the first success.
- Use Generic HTTP Webhook or Feishu/Lark custom-bot text messages, with optional
  Bearer authentication or bot signing. Select channels per endpoint, or use all
  configured channels by default; an explicit empty list sends none.
- Persist incidents and notification tasks with bbolt or Redis. Pending deliveries
  resume after restart; confirmed incidents survive restarts, while unconfirmed
  failure counts reset. Recovery uses the original incident's channel snapshot
  and waits for its DOWN delivery on that channel.

## Configure and upgrade

Alerts are **disabled by default**. Start with the
[official YAML example](https://github.com/librecosta/uptime/blob/v0.2.0/configs/uptime.example.yaml): set `alerts.enabled`
to `true`, define stable IDs in `alerts.channels`, and optionally set each
endpoint's `alert_channels`. Run `uptime config check --config ./uptime.yaml`
before starting and restart after changes. Configuration checks are offline.
Keep Webhook URLs, Bearer tokens and bot secrets private; environment variables
are resolved only for enabled, active configuration branches.

Existing monitoring configurations remain valid. Monitoring `uptime.db` Schema v1
is unchanged; alerts use a separate sibling `alerts.db` (independent Schema v1),
or an independent namespace in the configured Redis database. Stop the process
and back up **both bbolt files together**, including when alerts are later disabled.
Redis backup uses its operator-managed RDB/AOF procedures. Follow the
[Docker](https://github.com/librecosta/uptime/blob/v0.2.0/docs/deployment/docker.md#stop-maintain-back-up-and-upgrade) or
[systemd](https://github.com/librecosta/uptime/blob/v0.2.0/docs/deployment/systemd.md#stop-back-up-maintain-and-upgrade) guide for
permissions, shutdown budgets and restore steps. No automatic migration or backup
is performed, and service history exports are not database backups.

## Delivery limits

- Run **one alert executor per database/Redis prefix**; there is no distributed
  ownership or failover. Notifications do not affect monitoring readiness.
- Delivery uses at-least-once semantics with **at most ten attempts** and capped
  exponential backoff. Lost responses or crashes can cause duplicate messages;
  Webhook receivers should deduplicate by the stable EventID. Delivery is not
  guaranteed, and SENT means adapter acknowledgement, not human receipt.
- Keep channel IDs/configuration available for historical incidents. A missing
  channel retains its pending tasks; changing an ID does not reroute old tasks.
- There is no separate management UI. Alerts cannot detect this monitor stopping
  completely; use independent external health checks for the monitor itself.

## Downloads

Download Linux/macOS amd64 and arm64 archives, Windows amd64, and `SHA256SUMS`
from [GitHub Releases](https://github.com/librecosta/uptime/releases/tag/v0.2.0).
Verify checksums before extracting; the archives include the binary, example
configuration, README, MIT license and dashboard preview.
The matching container image is `ghcr.io/librecosta/uptime:v0.2.0` for Linux
amd64/arm64. See the deployment guides above for configuration and persistent data.
